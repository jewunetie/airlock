# eval/

Measurement harness for the numbers cited in `airlock.py`'s docstrings. This
is not part of the shipped tool: `airlock.py` runs standalone with nothing
here. `eval/` exists so those numbers can be checked rather than taken on
faith.

## The dataset is not committed

`eval/dataset.jsonl` is generated, never checked in. `.gitignore`'s `*.jsonl`
rule covers it, and that rule stays in place on purpose.

Reason: the dataset's credentials category needs text that LOOKS like a real
API key, GitHub token, or private key to test whether the guard catches it.
A hand-picked example close enough to a real shape can trip secret scanning
even though it is fake, which is exactly what happened to this project once
(see `CLAUDE.md`, "Credentials in tests are generated, never written down").
So `build_dataset.py` builds every credential example from a real vendor
prefix plus a body generated by `random.Random(seed)`, the same approach
`fake_credential` / `CREDENTIAL_SHAPES` use in `tests/test_server.py`.
Nothing that could pass for a live credential is ever a literal in this repo.

Regenerate it before running anything else:

```
uv run --script eval/build_dataset.py
```

Same seed, same output, every time: the default seed is fixed, and passing
`--seed N` explicitly still reproduces deterministically for that seed. The
script asserts 320 records, 8 categories, 20 block and 20 approve each, and
fails loudly if that shape breaks.

## Reproducing the claims in airlock.py

All commands below are run from the repo root.

**Detection rates by padding shape** (`reassembles_identifier`'s docstring:
"drove detection to 0.00" before the fix, "back to 1.00 on all four padding
shapes" after it):

```
uv run --script eval/padding_bypass.py
```

The "Detection" table's `shipped` column (whole-value matching, no
digits-only projection) reproduces the 0.00 collapse under suffix, prefix,
both-sides, and prose padding. The `digits` column (the projection that
shipped) reproduces the recovery to 1.00 on the same four shapes.

**False-blocking rates by round shape** (same docstring: "0.000 false
blocking measured on six legitimate round shapes"):

The same run's "False blocking" table shows the `digits` column at 0.00
across the three round shapes this script exercises (numeric, prose, mixed).
The docstring cites six shapes including one built from twelve 16-digit
values; that specific shape is not one of the three here. It is instead
pinned as a deterministic regression assertion in `tests/test_round_guard.py`
(`twelve_16digit_values` against a sixteen-`9`s source), which this eval/
harness does not touch and which is exercised by `tests/test_round_guard.py`
directly, not by anything in `eval/`.

**The rejected substring-DP design's numbers** (same docstring: the
alternative "letting each value contribute any contiguous substring instead
of only whole values" is `substr` here; `padding_bypass.py`'s own docstring
names it explicitly):

The same run's `substr` column in the false-blocking table shows a
meaningfully worse rate than `digits` on the numeric round shape (this
snapshot measured roughly 12%, in the same range as the 12.8% the docstring
cites). Its detection column stays at 1.00 for every padding shape, same as
`digits`; the difference the design was rejected for shows up only in false
blocking. The docstring's specific "100% false blocking" figure was measured
against the sixteen-digit-values shape, which again is not one of this
script's three round shapes, so that exact number is not reproduced by this
command; the direction and rough magnitude are.

**The six-digit-floor residual** (same docstring: "300 seeded trials
(eval/reassembly_residuals.py), 20/40/60 six-digit sources against such a
round: 0.0000 to 0.0133 false blocking for the shipped function, 0.0000 to
0.0067 for the raw pass alone... eight- and nine-digit sources measured 0.000
for both"):

```
uv run --script eval/reassembly_residuals.py
```

The "Six-digit-floor residual" table varies source length (six, eight, nine
digits) and source count (20, 40, 60) against a digit-dense round of prose,
amounts, dates, box numbers and reference numbers, over 300 seeded trials per
cell, for the shipped `reassembles_identifier` and for its raw pass in
isolation. A run against this repo's `dataset.jsonl` (seed 20260817) measured
eight- and nine-digit sources at 0.0000 for both columns, and six-digit
sources at 0.0000 to 0.0133 (shipped) and 0.0000 to 0.0067 (raw pass) across
the three source counts, matching the docstring as it now reads. The
digit-dense round produces literal digit runs in its own right (dates,
amounts, box and reference numbers concatenated in job order can abut without
a separator), so the raw pass false-blocks at the six-digit floor too, not
only the digits projection; the projection adds to that floor rather than
creating it on its own. The docstring was updated to this run's figures, so
`airlock.py`'s prose and this script now agree.

**`MAX_REASSEMBLY_LENGTH`'s worst-case timing** (the comment above the
constant: 18.0 seconds pre-bound was the historical measurement that
motivated the bound; post-bound, at the bound's own ceiling against 400
workspace identifiers, the function still costs seconds because cost scales
with identifier count as well as total length):

```
uv run --script eval/reassembly_residuals.py
```

The same run's "MAX_REASSEMBLY_LENGTH worst-case cost" section times the real
`reassembles_identifier`, not a scratch reimplementation. It cannot reproduce
the pre-bound scenario directly: 12 values of `FILE_SLICE_CHARS` each sum to
48,000 characters, and `MAX_REASSEMBLY_LENGTH` itself now rejects a round
that large in O(1) before the expensive subset enumeration runs at all, which
is the entire reason the comment gives for the bound existing; 18.0 seconds
is carried in the comment as that historical justification, not as a figure
this script reproduces. What this measures instead is the worst case the
CURRENT, bounded function can still be made to pay: 12 values summing to
exactly the `MAX_REASSEMBLY_LENGTH` ceiling (4,000 characters total, so the
length check does not short-circuit) against 400 non-matching workspace
identifiers (so neither the raw pass nor the digits projection exits early
on a hit). This run measured a mean of 4.452 seconds (median 4.416 seconds)
over 5 reps, matching the figure now in `airlock.py`'s comment. Cost scales
with identifier count, not only length: a shaped round (twelve 80-character
values, well under the ceiling) against a realistic handful of workspace
identifiers costs tens of milliseconds, not seconds; this script does not
vary identifier count itself, so that scaling claim was checked separately
against the real functions and is stated qualitatively in the comment rather
than pinned to a script-reproduced figure. Re-measure the ceiling timing
before trusting it on your own machine; see "Sandbox versus Apple Silicon"
below.

`tests/test_round_guard.py`'s `important3_length_bound` remains the
permanent regression control for this: it asserts the bound fires on an
oversized round and that a realistic round stays under it. It checks the
logic, not the timing; `reassembly_residuals.py` is what checks the timing.

## Sandbox versus Apple Silicon

Any latency number from a run in a constrained container does not transfer.
The original measurement ran on aarch64 without native bf16 matmul, so torch
fell back to BLAS gemm and one config measured 603ms mean per message under
that fallback. Apple Silicon has native bf16 and will be substantially
faster. Re-measure on the machine you care about before treating any latency
figure as real; only detection and false-blocking rates are meant to
transfer across hardware.

## What each script does

- `build_dataset.py` builds `dataset.jsonl`: 320 synthetic records across 8
  categories, half block-worthy and half approve-worthy, credentials
  generated rather than literal.
- `padding_bypass.py` measures the fix for the suffix-padding bypass in
  `reassembles_identifier`: detection by padding shape and false-blocking by
  round shape, for the shipped design and two candidates that were not
  shipped.
- `reassembly_residuals.py` measures two claims `padding_bypass.py` does not
  cover: the six-digit-floor false-blocking residual in
  `reassembles_identifier`'s docstring, and the worst-case timing cited above
  `MAX_REASSEMBLY_LENGTH`. Imports the real functions; times the real
  function at its bound rather than a pre-bound scenario the shipped code no
  longer reaches.
- `round_guard.py` measures the round-level guard using the two 350M
  encoders alone (no deterministic layers), showing that reassembly
  detection dilutes as benign jobs are added to a round. This is the
  measurement that ruled out an encoder-only round guard.
- `round_full_stack.py` measures the same reassembly cases through airlock's
  actual stack (`scan_secrets` and `scan_pii_patterns` ahead of the
  encoders), attributing each catch to the layer that made it.
- `bakeoff.py` is the single-message guard-architecture comparison across
  configs (PII Detector, Policy Linter, Privacy Filter, and combinations).
  Provenance for the dataset's design and for the architecture conclusions
  in the project's planning notes; not directly cited by number in
  `airlock.py`.

`round_guard.py`, `round_full_stack.py`, and `bakeoff.py` depend on
`torch`/`transformers` and download real model weights on first run; their
PEP 723 headers declare that, which is why the shipped `airlock.py` does not
depend on any of it.
