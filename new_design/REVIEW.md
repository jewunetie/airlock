**Findings that affect the protocol.**

1. **High: default reassembly geometry can reject ordinary prose through resource exhaustion.** With the protected source “The confidential acquisition is planned for November.”, the ordinary reply “The quarterly forecast includes inventory and shipment totals.” completed. The next reply, “The team will review the calendar and budget next week.” raised `reassembly_complexity_limit`. Two other protected sentences hit the limit on the third benign reply. These cases used the source's default minimum fragment length of two, fraction 1.0, and 20,000-state bound. They fail closed, but fail legitimate work. Increasing the minimum to three avoided these particular cases and then allowed `91`, `28`, `47`, `73`, `1` to reconstruct a declared `912847731` across releases. Raising a threshold alone is therefore an incomplete remedy. This is an availability and coverage tradeoff requiring a representative evaluation, not a measured production failure rate. [Fragment extraction and check](/Users/jewunetie/Projects/airlock/new_design/airlock.py:1083).

2. **High: the release review omits the question and disclosure purpose.** Its payload contains only `candidate`, `findings`, and `failures`. A human reviewing “yes” cannot assess what that answer reveals without retrieving separate history. The candidate, original request, disclosure purpose, selected workspace, and relevant policy should appear together for an informed decision, and the approval should bind the decision-relevant context. The test verified that a manual vote is one-use and also verified these missing fields. [Review payload](/Users/jewunetie/Projects/airlock/new_design/airlock.py:1361).

3. **Security limit: source completeness remains controlled by the model.** When `912`, `84`, and `7731` were released with no source declaration, all three completed. When only the first fragment preceded the declaration of `912847731`, all three still completed. The ledger does not retroactively match earlier output against newly learned sources. A model can also falsely declare a public word as protected; a receipt-only task declaring “forecast” caused a later ordinary “forecast” answer to be withheld. These tests used a clean scanner fixture to isolate the reassembly contract. They do not demonstrate that real detectors would miss every example. Model declarations are helpful evidence but cannot support a completeness guarantee. [Source registration](/Users/jewunetie/Projects/airlock/new_design/airlock.py:1317), [source registry](/Users/jewunetie/Projects/airlock/new_design/airlock.py:1067).

4. **Security limit: cumulative protection has a raw-source availability condition.** After releasing `91284`, closing and reopening the real SQLite store, a new registry allowed `7731` when the source was absent. Re-declaring the source correctly withheld that fragment. Durable HMAC identifiers reconnect known sources; they cannot reconstruct a missing source string. The same loss of raw matching state occurs when the last runtime stops and shared resources are cleared. The architecture already acknowledges restart limitations; the public promise should carry the condition explicitly. [Shared teardown](/Users/jewunetie/Projects/airlock/new_design/airlock.py:3376).

5. **High for write workflows: retries can create a second logical task.** Two identical legacy submissions queued two different tasks. Native task identity can deduplicate framework delivery, but the three-tool API has no portable client request identity for the response-lost case. Instructions telling a caller to avoid resubmission do not define replay handling. A request identity, payload-conflict rule, and retention scope belong in the protocol. Repeated polling of an already committed result should preserve the same result. No writes were executed in this test. [Submission](/Users/jewunetie/Projects/airlock/new_design/airlock.py:2918), [native identity mapping](/Users/jewunetie/Projects/airlock/new_design/airlock.py:3240).

6. **Privacy limit: short answers can carry a sensitive meaning without sensitive wording.** “yes” passed the isolated release path even when a private diagnosis sentence was registered. The scanner receives the answer text alone. A yes/no answer, count, ranking, or paraphrase can disclose a fact through its relationship to the question. The protocol needs to state what information is authorized to leave and preserve that semantic context during review. Text classification and fragment matching provide additional detection, with measured limits. [Candidate inspection](/Users/jewunetie/Projects/airlock/new_design/airlock.py:1330).

7. **Medium: task limits do not bound persistent input history.** With an active-task cap of one, ten rejected submissions still created ten additional interaction records. A 32,000-character request rejected by the configured request limit was still retained in full. Indefinite logging is documented, but an untrusted authenticated caller can consume storage without creating useful work. Admission and storage budgets, plus an intentional retention policy, are needed for robustness. No disk-exhaustion attempt was made. [Log-before-admission behavior](/Users/jewunetie/Projects/airlock/new_design/airlock.py:2922).

**Simplicity and opinionated behavior.** The caller API is simpler. Installation and local operation still involve a supervisor, authenticated loopback server, stdio bridge, SRT, worker and scanner processes, an inference service, four scanners, provisioning manifests, calibration, and a database. The strict preset prompts for requests and individual reads as well as release; the TUI exposes policy editing as JSON. Those choices should be tested as a user's actual workflow before calling the experience easy.

My recommendation for a narrow baseline is a locally selected workspace, OS-enforced read-only capability by default, ordinary scoped reads covered by admitted work, explicit decisions for writes and shell capability, and an informed local decision for every disclosure. Expanding to automatic disclosure changes the assurance claim and needs separate evaluation. Security checks can remain fail-closed while their false blocks and availability limits are assessed. The pending product question is whether per-disclosure review is acceptable in normal use.

**What a security protocol specifies.** A protocol describes the obligations of interacting parties: roles, authentication, message formats, state transitions, allowed observations, authorization, errors, replay behavior, cancellation, recovery, bounds, and version compatibility. An implementation selects libraries, models, storage, and UI to satisfy those obligations. Start with the attacker capabilities and the exact properties claimed; recognized security guidance emphasizes both covered threats and explicitly excluded threats. [RFC 3552](https://www.rfc-editor.org/rfc/rfc3552.txt).

For Airlock, useful baseline invariants would include:

- The caller's request and disclosure purpose cannot grant local capabilities or change policy.
- Every worker subprocess has the configured filesystem and network restrictions; no authorized tool escapes that boundary.
- No model-authored answer is published without an explicit disclosure request and locally valid release authorization.
- Approval identifies the exact disclosure and its meaning-bearing request context, under a specific policy version.
- Cancellation before release commit prevents publication. Cancellation after commit does not retract delivery or undo completed writes.
- A permitted retry reuses a logical task; conflicting reuse fails.
- Published content is committed with the required disclosure state before delivery. A crash may conservatively count undelivered content.
- Status and error surfaces have an enumerated metadata allowance. Timing, counters, labels, and refusal patterns are observable, even when no answer is returned.
- Restart, source-registration timing, and enforcement bounds have explicit behavior. Tests cover both successful work and refusal paths.

These are candidate protocol requirements for discussion, not implemented changes or an agreed final specification. The present code establishes several core invariants in isolated tests and leaves other conditions open. A guarantee that no private meaning can ever escape arbitrary model output is not established by these mechanisms.

**Signal as an example.** Signal separates initial key agreement, ongoing message encryption, and multi-device session management into published specifications. PQXDH establishes a shared secret using prepublished key material, enabling a sender to contact an offline recipient. Identity-key authentication requires an appropriate verification method. The Double Ratchet derives fresh message keys and updates shared key material to limit the damage of key compromise. Current specifications also describe post-quantum and Triple Ratchet constructions. [Signal specifications](https://signal.org/docs/), [PQXDH](https://signal.org/docs/specifications/pqxdh/), [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/).

Signal's recipient is intended to recover the plaintext. Airlock's problem is deciding which information an external recipient should be allowed to learn. The useful lessons are precise claims, explicit state, replay handling, bounded work, and analysis of the resulting construction. A formal analysis of Signal's earlier core proves properties in a stated model; it does not certify every later implementation or all endpoint behavior. [Formal Signal analysis](https://www.douglas.stebila.ca/research/papers/JC-CCDGS20/).

**Distribution.** Publish an implementation-independent, versioned Airlock specification with schemas and conformance cases. Distribute a reference implementation through ordinary signed/reviewable software releases and pinned artifacts, with MCP as a transport binding and a plugin as client integration. The baseline should define what qualifies as conforming and how capability/version changes are handled. Models, scanners, Pydantic, SQLite, and Textual can remain replaceable implementation choices, with their operational assurance recorded separately. External review and target-platform tests supply evidence beyond a self-reported passing suite.

Signal illustrates this split: public specifications describe protocol behavior; `libsignal` supplies Rust implementations exposed through Java, Swift, and TypeScript interfaces. Its maintainers explicitly state that use outside Signal is unsupported, so it is an example of the distinction between publishing a protocol and promising a supported general-purpose SDK. [libsignal](https://github.com/signalapp/libsignal).
